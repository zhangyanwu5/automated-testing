# AI 自动化测试体系说明（从零视角）

本文档描述**目标能力**与**概念模型**，不绑定任何具体技术栈、仓库结构或已实现模块。工程落地路线见 [ROADMAP.md](./ROADMAP.md)；流水线、落盘与门禁契约见 [ATF_PIPELINE_AND_SCAN_SPEC.md](./ATF_PIPELINE_AND_SCAN_SPEC.md)。**逻辑部件与数据流**见 [TECHNICAL_OVERVIEW.md](./TECHNICAL_OVERVIEW.md)。

---

## 1. 背景与定位

「AI 自动化测试」不应窄化为「让模型代写脚本」。更完整的含义是：围绕**需求、实现、运行环境、真实交互与证据**，形成可重复、可解释、可扩展的自动化闭环。

对游戏类软件（复杂 UI、状态机、脚本与引擎混合逻辑、长流程、高频迭代），体系目标通常包括：

- 理解需求与验收口径  
- 分析或索引实现侧信息（代码、配置、资源关系等）  
- 生成或维护可执行的测试资产  
- 驱动被测程序在真实或近真实环境中运行  
- 采集日志、画面、内部状态等**证据**  
- 判定功能与体验是否符合意图  
- 区分环境/脚本问题与产品缺陷，并支持回归与（可选）修复闭环  

理想终态可概括为：

```text
需求与实现认知 → 生成测试 → 编排运行 → 判定与归因 → 报告与回归 →（可选）修复与再验证
```

是否引入「AI 自动改产品代码」由组织策略决定；**测试体系本身**应先把「发现、分类、留证、回归」做扎实。

## 2. 两个核心测试视角

### 2.1 开发者视角：规格与正确性

关注：**行为是否按需求与设计正确实现。**

核心问题：

> 在声明的前提下，该功能是否满足规格？

典型覆盖：

- 流程完整性、业务规则、状态迁移  
- 边界与异常输入、模块协作  
- 回归：新改动是否破坏既有行为  

常见测试形态（概念上，非互斥）：单元、集成、契约、功能/业务流程、状态校验、回归等。

理想信息流：

```text
需求与验收项
  ↓
拆解为可验证点与用例草案
  ↓
结合实现认知（扫描/分析结果）细化步骤与数据
  ↓
编排：环境就绪 → 执行步骤
  ↓
判定（确定性断言 + 必要时语义判定）
  ↓
失败：归因、证据、是否进入修复/重跑
```

### 2.2 玩家视角：路径与体验

关注：**真实或近真实操作下，体验是否自然、稳定、可理解。**

核心问题：

> 玩家能否顺畅完成目标？反馈是否可信？是否会卡死、误导或挫败？

典型覆盖：端到端路径、UI 自动化、玩家旅程、探索式与长稳、兼容性维度等。

理想信息流：

```text
测试目标（场景/旅程）
  ↓
规划操作路径与观测点
  ↓
编排：环境就绪 → 输入驱动（点击/输入/时序）
  ↓
观测：画面、可访问性树、日志、内部状态
  ↓
判定（规则 + 可选视觉/语言模型辅助）
  ↓
记录问题类型与证据
```

### 2.3 运行时：从「空环境」到「可验收」

自动化**默认不能**假设「已经有一局正确状态的游戏」。体系应显式建模一条可编排、可超时、可重试、可写入报告的链路：

```text
启动工具链 / 引擎侧进程
  ↓
启动被测应用或进入可驱动会话，建立控制与观测通道
  ↓
满足「测试环境与前置条件」（见下）
  ↓
执行针对需求或场景的步骤与判定
```

**测试环境与前置条件**指：在进入「验收该需求」的步骤之前，世界状态、账号会话、服务端数据、功能开关等必须满足用例声明。例如：指定服登录、角色进度、背包门槛、活动阶段等。

前置未满足时的失败，应与「功能逻辑不符合规格」**分类记录**，避免将登录失败误判为业务逻辑错误。该语义与《流水线规格》中执行阶段的分段、报告字段一致。

### 2.4 宿主形态与控制—观测路径（与 Web 自动化对照）

游戏自动化常与 **Web 端 Playwright 一类工具**对照理解，但**宿主与协议不同**，ATF 体系在规格层应区分三条路径（细节与原理见 [Playwright原理与Web游戏自动化对照.md](../Playwright原理与Web游戏自动化对照.md)）：

| 形态 | 控制与观测大致落在 | 对「玩家视角」的含义 |
| --- | --- | --- |
| **浏览器内 Web 应用** | DOM / 可访问性树、浏览器事件管道、DevTools 类协议；强 Locator + 自动等待模型 | 与 Playwright 生态一致，**不是**本文默认宿主 |
| **WebGL 等发布在浏览器内的游戏** | 仍受浏览器外壳约束；画布内往往**难**稳定 DOM 定位，**通常拿不到**任意游戏内状态 | 可叠浏览器工具做键鼠与截图级验证；深度状态仍宜 **引擎内桥接** 补充 |
| **原生引擎客户端（Unity / UE 等）** | 无 HTML DOM；宜 **进程外测试编排 + 与游戏进程的长连接或 RPC**，配合 **引擎内输入管线注入** 与内部状态读取 | 「像玩家」应优先走 **官方输入与 UI 驱动路径**（如引擎测试框架、元数据定位），而非默认依赖全局 OS 键鼠模拟 |

**可借鉴、但不照搬的设计要点**（与上述对照文一致）：测试 API → 会话/命令层 → **宿主适配**；轻量隔离（对标快速重置场景/存档/实例）；**智能等待**（Ready 标志、网络、动画，少写死固定 sleep）；**稳定定位**（路径/元数据/组件 id，慎用易碎索引）。ATF 的「工具链 → 应用 → 前置 → 验收」编排即对应「会话建立 → 目标就绪 → 动作与断言」的跨宿主抽象。

## 3. 扩展维度

### 3.1 稳定性与异常

除「对错」外，还需「是否活着、是否干净」：

崩溃、卡死、断线、黑屏、异常日志、资源与长时间漂移、重复执行一致性、随机扰动下的健壮性等。

能力簇包括：崩溃/日志类判定、超时与心跳、截图留证、巡检与随机探索等。

### 3.2 回归与基线

改动可能修复 A、破坏 B。体系应能沉淀**核心路径与历史缺陷用例**，并支持基线对比（状态摘要、日志指纹、画面指纹、结果历史），回答「是否新增失败、是否与已知失败同类」等问题。

### 3.3 语义与视觉判定

许多游戏问题难以用 `actual == expected` 表达，例如布局明显错位、停在错误界面、提示语义含糊等。可引入**语义判定器**（例如基于多模态证据的 PASS/FAIL/UNKNOWN），并强制：**理由、置信度、建议补充证据**，且 UNKNOWN 不得默认当 PASS。

**与像素级截图回归的关系**：业界默认的截图回归多为 **基准帧 + 当前帧 + 像素/区域差异 + 容差与掩膜**（与 Playwright 视觉对比同类），**不等同于**大模型看图。语义 / VLM 判定是**可选增强**，用于规则与像素难以覆盖的体验类问题；两者在成本、稳定性与可解释性上应**分轨设计**，报告中宜区分证据类型。

### 3.4 自动修复（可选终态）

在证据、归因、回归稳定之后，可探索：失败聚合 → 根因假设 → 定位变更点 → 生成补丁草案 → 目标用例重跑 → 子集回归 → 审计与人工门禁。该路径涉及权限与安全策略，应**默认保守**（如仅建议、或仅限测试资产自动修复）。

## 4. 能力分层（概念）

自下而上可理解为：

```text
运行与环境层
- 引擎/进程编排、就绪探测、控制通道
- 前置条件声明、执行、超时与重试
- 前置失败与验收失败的分类

需求与实现认知层
- 需求结构化、验收项、与用例的映射（追溯）
- 代码/脚本等扫描与分析产物，为生成与归因服务

正确性与流程层
- 开发者视角用例与确定性判定

体验与路径层
- 玩家视角路径、观测与体验相关判定

稳定性与回归层
- 异常检测、基线、趋势、 flaky 识别

智能闭环层（按需）
- 语义判定、卡点归因、脚本侧自动修复、（可选）产品侧修复建议
```

各层可**分阶段建设**；上层依赖下层提供的证据与编排能力。

---

## 5. 建设原则（与实现无关）

1. **先编排，后炫技**：引擎→应用→前置→验收的链路与报告分段优先于复杂生成。  
2. **证据优先**：任何 FAIL 应能指向日志、截图、状态快照等可追溯引用。  
3. **类型不静默省略**：计划与生成物应对「全量测试类型枚举」逐条给出可执行或跳过及原因（见《流水线规格》）。  
4. **归因分桶**：脚本/环境/产品三类边界清晰；产品缺陷不允许靠改断言「糊弄通过」。  
5. **人机协同**：高成本或高风险的自动化（LLM 改代码、自动合并）保留人工确认与策略开关。  
6. **宿主正确性优先**：按 2.4 选择控制面（浏览器内 / WebGL / 原生）；原生客户端优先 **引擎内输入与状态观测**，再考虑 OS 级黑盒模拟等特例场景。  
7. **实现合理化**：代码与仓库结构以**可读、可测、分层与依赖方向清晰**为先；扩展点与宿主/分析器种类增多时，接口与注册机制与问题规模匹配；契约与报告始终严格（详见 [TECHNICAL_OVERVIEW.md](./TECHNICAL_OVERVIEW.md) §2）。

## 6. 推荐阶段目标（产品阶段）

### Phase 1 — 可执行闭环

```text
需求 + 实现认知 → 可执行用例（含前置声明）→ 编排运行 → 基础判定 → 结构化报告
```

重点：前置与验收分段、报告 schema、最小追溯（用例 id、需求引用）。

### Phase 2 — 体验与智能判定

```text
路径与观测丰富 → 语义/视觉判定接入 → 证据友好的报告与 UNKNOWN 策略
```

### Phase 3 — 回归运营

```text
基线存储 → diff 与历史 → flaky 与趋势
```

### Phase 4 — 闭环加深

```text
卡点归因 → 脚本侧修复与受控重跑 →（可选）产品修复原型与审计
```

阶段与里程碑的对应关系见 [ROADMAP.md](./ROADMAP.md)。

## 7. 文件索引与 AI 语义层（自动化知识包 AKP）

「理解项目 + 策划案以便后续自动化」在工程上拆为两层（详见 [AUTOMATION_KNOWLEDGE_AND_AI_LAYER.md](./AUTOMATION_KNOWLEDGE_AND_AI_LAYER.md)）：

- **L0**：`scan_index` 等 —— 回答「哪些文件、变没变、策划指纹是否最新」，为 Agent 提供**事实锚**，避免编造路径。  
- **L1**：**自动化知识包（AKP）** —— 在 L0 + PRD 之上，由 Agent / 大模型与可选检索生成**结构化、可版本化**的 JSON，覆盖用例草案、前置、断言线索、执行提示、风险与 `unknowns` 等，供矩阵、Unity `-executeMethod`、报告与卡点分析消费。

全自动化终态下，流水线应在门禁通过后**可选或必选**地生成/更新 AKP，再进入矩阵与执行；具体策略（阻断 vs 降级）由项目配置决定，须在实现文档中写死。

---

## 8. 总结

两条主线：

```text
开发者视角：规格与正确性
玩家视角：路径与体验
```

成熟体系还需显式包含：**运行编排与前置**、**稳定性**、**回归与基线**、**语义判定**、以及按需的**修复闭环**。
