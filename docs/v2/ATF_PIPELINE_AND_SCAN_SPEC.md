# ATF 流水线与增量扫描 — 产品规格（v2 · 从零视角）

本文档固化**产品契约**：工具如何被调用、数据如何落盘、一次完整执行包含哪些阶段、报告必须区分什么。不假设已有 CLI、模块名或仓库布局；实现语言与栈可自定，**须满足本文契约并与《技术总览》工程原则一致**（分层与依赖方向、可观测、契约与版本化等，见 [TECHNICAL_OVERVIEW.md](./TECHNICAL_OVERVIEW.md) §2）。

**体系语境**（测试类型与能力分层）以 [AI_AUTOMATED_TESTING_SYSTEM.md](./AI_AUTOMATED_TESTING_SYSTEM.md) 为准。  
**分阶段交付顺序与里程碑编号**以 [ROADMAP.md](./ROADMAP.md) 为准。  
**逻辑部件与数据流**以 [TECHNICAL_OVERVIEW.md](./TECHNICAL_OVERVIEW.md) 为准（实现映射时的参考分解）。

---

## 1. 背景与目标

ATF 应可通过**自动化入口**（CLI、CI 任务、或包装脚本）驱动，形成两条清晰能力：

1. **项目扫描**：对工程做可记录、可复用的分析索引，并支持基于**文件内容哈希**的增量扫描，避免每次无差别全量重复分析。  
2. **执行自动化测试**：在「代码侧索引与需求文档均为当前版本下的最新认知」这一前提下，生成多类型测试所需材料；执行时完成 **启动工具链 → 启动被测应用 → 环境与前置条件就绪**，再调度具体测试任务、产出报告；遇**卡点**时由 **AI 辅助归因**，区分**测试资产/编排问题**与**被测产品缺陷**，后续动作遵循约定优先级（脚本侧可修复则优先修复脚本并重跑受影响范围，产品缺陷不得靠篡改断言假通过）。

允许**分阶段交付**：每一阶段在生成物中**覆盖全部约定测试类型**；尚未落地的类型以明确状态与原因标出，**不得静默省略**。

---

## 2. 产品形态：入口与模式

- 单一入口应能区分至少两种模式：  
  - **仅扫描**：给定项目根（及可选配置），更新项目内持久化扫描数据。  
  - **执行自动化测试**：给定项目根与需求文档路径（当前规格约定需求为 **Markdown**），先满足「最新」门禁，再生成结构化产物、编排运行、写报告。  

具体命令名、子命令与 flag **不在本规格中锁定**；实现阶段自由命名，只要行为符合本文各节。

## 3. 项目扫描

### 3.1 行为

- **首次或强制全量**：在约定的源码范围内遍历，执行分析（解析、符号、调用关系、或项目自定义规则），并持久化。  
- **后续执行**：读取持久化索引，用**逐文件内容哈希**识别变更；对新增、删除、内容变化的文件重新分析；未变化文件复用或轻量校验，实现**增量扫描**为主。

### 3.2 记录内容

- 持久化格式：**JSON**（索引或清单，可拆多文件）。  
- 至少**逐文件**记录：路径、内容哈希、与增量相关的元数据；可选附分析摘要或指向 `artifacts/` 中详情的引用。  
- 索引中须包含**规则版本**或分析器/插件版本标识；版本升级时触发**失效或部分重扫**策略，避免错误复用。

### 3.3 扫描范围（规格层约定）

默认面向**游戏客户端常见组合**：**C# 与 Lua**（各自扫描根由项目配置给出）。其他语言可按项目扩展，但须在索引与规则版本中可区分。

### 3.4 存储位置

所有扫描索引、中间产物、运行报告等，**默认存放在被测项目根目录下**（而非 ATF 工具自身安装目录），以便版本管理与 CI 缓存策略由项目方决定。

### 3.5 语义认知层（可选，与 §3.1–3.2 区分）

**文件级扫描（§3.1–3.2）**回答：路径集合、内容哈希、规则版本、增量复用；**不**等同于「模型已理解事件/协议/业务规则」。

**语义认知层（L1）**在门禁通过且具备 `scan_index` + 需求 Markdown 的前提下，由 **AI / Agent** 生成 **自动化知识包（AKP）**：结构化描述需求理解、代码/Lua 表层、用例草案、执行提示与风险等，供矩阵、宿主执行与报告消费。**契约、字段、工程化原则**见 [AUTOMATION_KNOWLEDGE_AND_AI_LAYER.md](./AUTOMATION_KNOWLEDGE_AND_AI_LAYER.md)。AKP **不得**替代 freshness；默认落盘于 `.atf/artifacts/`（见 [ATF_DIRECTORY.md](./ATF_DIRECTORY.md)）。

### 3.6 项目内目录根名（已拍板）

统一使用项目根下 **`.atf/`**，建议子结构示例：

- `scan_index.json`（或等价名）— 扫描索引  
- `artifacts/` — 分析片段、中间 JSON  
- `reports/` — 运行报告、卡点分析等  

子路径与命名可由实现细化；**根目录名 `.atf/`** 为本规格固定契约。目录与 `.gitignore` 建议见 [ATF_DIRECTORY.md](./ATF_DIRECTORY.md)。

## 4. 「是否最新」门禁

在「执行自动化测试」或任何依赖扫描结果的流程前，须判定当前是否已基于**当前工作区**完成有效认知：

- **代码侧**：索引中的逐文件哈希与规则版本与当前磁盘一致；否则先执行（以增量为主的）扫描。  
- **需求侧**：需求为 Markdown；参与 freshness 判断（建议路径 + 内容哈希，策略与代码侧对称）。  

逻辑归纳：**代码索引最新 ∧ 需求文档最新 ∧ 规则版本一致**（或与实现约定的等价条件）才允许进入「生成与执行」；否则先补齐扫描或更新需求指纹。

### 4.1 实现边界（M2 对齐）

- **仅改需求、不改扫描范围内代码**：整体门禁仍视为**不最新**，直至索引中的需求指纹（路径 + 内容哈希）与磁盘一致；可通过「带需求路径的扫描」或「仅刷新 `prd` 指纹」类 API 更新，而无需重分析未改动的源码文件（若代码侧已仍与索引一致）。
- **仅改未纳入扫描范围的文件**：不改变**代码侧** freshness（索引不跟踪该路径）；若该文件即当前参与门禁的需求 Markdown，则**需求侧**仍会判定为不最新。
- **仅代码门禁**：调用方可不显式传入需求路径，此时实现**不**校验索引中的 `prd` 块是否与磁盘一致（与「执行自动化测试」全量门禁区分，供 CI 复用）。

## 5. 执行自动化测试：阶段（已确认）

完整一次执行，按时间顺序包含：

**扫描门禁 → 生成结构化产物 → 运行时编排（工具链 / 应用 / 前置条件）→ 任务 DAG 执行 → 卡点分析**

### 5.1 阶段 1 — 扫描门禁

1. 按第 4 节检测是否最新。  
2. 若否：执行扫描（以增量为主）。  
3. 若是：进入下一阶段。

### 5.2 阶段 2 — 生成各类型测试所需内容

- **输入**：最新扫描结果 + 需求 Markdown。  
- **输出**：JSON（可多文件），须带 **schema 版本**字段。  
- **类型覆盖**：与《体系说明》中涉及的测试类型语境**严格对齐**（单元、集成、契约、功能、业务流程、回归、E2E、UI、玩家路径、探索式、体验、兼容性、长流程稳定性等；**精确枚举以《体系说明》与《Roadmap》中矩阵为准**）。  
- **前置条件**：生成物必须能表达进入验收前所需的游戏内/服务端状态（登录、等级、开关、背包等）；在报告与调度中可识别为**环境准备阶段**，不得仅隐含在某个点击步骤里。  
- **分阶段交付**：每一交付阶段，生成物中**必须出现全部类型**条目；尚不可执行的，使用如 `status: skipped` 并附 **`reason`**，**不得静默省略**。
- **（可选）自动化知识包 AKP**：在 `scan_index` 与需求 Markdown 已满足门禁的前提下，可由 AI / Agent 生成或更新 `.atf/artifacts/` 下的 **AKP JSON**（见 [AUTOMATION_KNOWLEDGE_AND_AI_LAYER.md](./AUTOMATION_KNOWLEDGE_AND_AI_LAYER.md)），作为矩阵填充、宿主入口与报告追溯的**附加输入**；AKP 失败时的策略（阻断 / 降级）须由实现与项目配置定义并文档化。

### 5.3 阶段 3 — 运行时编排

在进入针对需求的验收步骤之前，须完成：

1. **启动工具链 / 引擎侧**：按项目约定达到可启动被测应用的就绪状态（超时、重试、日志）。  
2. **启动被测应用**：构建包或编辑器会话等；建立控制与观测通道（RPC、WebSocket、注入桥等由实现选型）。通道在语义上可比照 **「进程外编排端—长连接或等价双向流—被控应用」**（与浏览器自动化中「客户端—Server—浏览器」分层同类，见 [Playwright原理与Web游戏自动化对照.md](../Playwright原理与Web游戏自动化对照.md) 第一节）；**不得**默认假设存在 DOM 或可访问性树，除非宿主确为 Web/WebGL 且已在需求与矩阵中声明。  
3. **测试环境与前置条件**：根据 5.2 中声明，顺序或并行完成直至谓词满足；本阶段结果**单独写入报告**。  
4. **就绪门禁**：前置未满足则不得开始验收步骤；失败原因须支持后续归因（脚本声明错误、环境不可用、产品缺陷等）。

### 5.4 阶段 4 — 任务顺序与并行

- **无依赖的任务可并行**；有依赖的须满足 DAG 前驱后再启动后继。  
- **5.3 运行时编排**在依赖上通常构成整次运行的**根层或独立层**（先就绪，再挂各测试类型任务）。  
- 建议在 JSON 或调度配置中为任务声明 `depends_on` 等；调度器按拓扑分层，**同层并行、跨层串行**，并检测环与配置错误。

### 5.5 阶段 5 — 卡点与 AI 分析

**业务要求：**

- 卡点可能来自**测试资产/编排**，也可能来自**被测软件**；须具备区分能力（可规则 + LLM）。  
- **脚本/编排类**：优先修复测试资产或生成可应用补丁，然后对**受影响子图**重跑。  
- **产品缺陷类**：不得通过改断言使失败变通过；报告中记录缺陷描述、证据链、复现与对产品的修复建议。

**卡点类别（建议报告字段）：**

| 类别 | 含义 |
| --- | --- |
| **硬卡点** | 无法继续，如连接断开、超时、崩溃、必要资源缺失、5.3 失败等。 |
| **软卡点** | 流程可继续或已结束，但判定未通过。 |
| **质量卡点** | 证据不足、判定 UNKNOWN 等，需补证据或人工确认。 |

**脚本 vs 产品（判别原则，供实现与 Prompt）：**

- 偏脚本：选择器/步骤/等待/环境与当前 UI 或真实环境不一致；修复不改变「产品是否满足需求」的语义，只修正「如何测」。  
- 偏产品：在脚本与环境合理前提下，行为稳定违背需求/设计，且多证据一致指向实现问题。

自动应用补丁的策略（阈值、仅测试资产、禁止写产品目录等）由实现与安全策略定义。

---

## 6. 报告

- 位置建议：`.atf/reports/`。  
- 须包含：概况、**5.3 各子阶段**耗时与结果、各类型任务状态（含 skipped+reason）、失败与卡点详情、**归因结论**（脚本/环境/产品等分桶）、建议的修复方向、证据引用路径。  
- **前置阶段失败**与**验收阶段失败**必须可分栏或分字段区分。
