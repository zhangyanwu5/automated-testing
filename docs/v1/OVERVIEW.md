# 框架概览

## 1. 要解决什么问题

大型游戏项目的自动化测试面临几个长期痛点：

- 状态空间巨大，脚本化测试覆盖率低
- UI 多为自绘，缺少可访问性树，断言困难
- 回归测试耗时，拖慢迭代
- 不同引擎（Unity / Unreal / Godot）各自维护一套测试体系
- 测试脚本与业务代码强耦合，业务一变就得重写

本框架的目标是：**把"编写和维护测试"这件事本身交给 AI 完成**，人只提供需求文档和项目代码。

## 2. 输入与输出

**输入**
- 需求文档（PRD / 设计案，自然语言）
- 项目代码（支持多种技术栈，如 Unity + C#、Unity + XLua、Unreal + C++ 等）

**输出**
- 针对该项目生成的测试适配器代码
- 基于需求自动合成的测试用例
- 测试执行结果与缺陷报告
- 可复用的回归测试资产

当输入信息不足以推进时，框架会主动发起交互式询问，而不是直接失败。

## 3. 能力边界

### 做的事
- 功能性测试（业务流程、UI 交互、状态校验）
- 探索式测试（自主发现崩溃、流程中断）
- 回归测试自动化
- 结构化缺陷报告与证据收集

### 不做的事
- 深度性能 profiling（交给 RenderDoc / Unity Profiler 等专业工具）
- 网络压测 / 负载测试
- 反作弊 / 安全测试
- 美术资源质量评估
- 真人可玩性的主观评价

## 4. 核心设计理念

### 4.1 AI 能力与框架解耦

框架不绑定任何具体的 AI 服务。LLM、VLM、代码生成等所有 AI 能力都通过标准接口接入，具体提供者（ClaudeCode SDK、Anthropic API、OpenAI、本地模型）作为可替换的实现。

这意味着：
- 项目不会因为某个 AI 服务停止维护或涨价而被绑架
- 新 AI 能力出现时可以快速集成
- 同一套框架可以在不同环境下选用不同的 AI 后端（公网 / 自部署 / 本地）

### 4.2 微内核 + 插件

核心只包含：接口定义、插件加载、服务注册、事件总线。所有具体功能——代码分析、适配器生成、测试执行、报告输出——都是插件。

这意味着：
- 扩展新引擎支持时，不需要改核心代码
- 不同项目可以按需加载插件组合
- 插件可以独立开发、独立升级

### 4.3 既能独立运行，也能嵌入

框架支持三种使用形态：

| 形态 | 场景 |
| --- | --- |
| 独立 CLI / 服务 | 作为独立工具使用，适合已有项目接入 |
| 作为库嵌入 | 被其他游戏开发框架（如公司内部统一开发平台）作为组件使用 |
| REST / MCP 服务 | 被 CI/CD、DevAgent 等外部系统远程调用 |

三种形态共用同一个核心，区别只在装配入口。

### 4.4 可观测优先于智能

AI 参与的每一个决策——代码分析结论、生成的适配器代码、测试用例合成过程、执行中的动作选择——都有完整的 trace 记录。

宁可让 AI 表现得"笨"一些但可追溯，也不要追求看似智能却无法审计的黑盒。

## 5. 演进路径

本项目不承诺日历时间，按阶段门控推进。每个阶段有明确的退出条件，达成后才进入下一阶段。

与 **v2 规格**的对照：工程上将「文件级扫描与门禁（L0）」与「面向自动化的语义认知包（L1 / AKP）」分层；后者在全自动化终态中位于门禁之后、矩阵与执行之前，契约与分阶段工程化见 [docs/v2/AUTOMATION_KNOWLEDGE_AND_AI_LAYER.md](../v2/AUTOMATION_KNOWLEDGE_AND_AI_LAYER.md) 与 [docs/v2/AI_AUTOMATED_TESTING_SYSTEM.md](../v2/AI_AUTOMATED_TESTING_SYSTEM.md) §7。

### Phase 0 · PoC 验证
- 在一个真实 Unity 项目上跑通最小闭环：PRD + 代码 → 自动生成一个可执行的测试用例 → 产出报告
- 验证 AI 代码分析与生成的可行性边界
- 退出条件：最小闭环跑通，且生成质量可接受

### Phase 1 · 核心框架
- 微内核、插件系统、服务注册、事件总线
- AI 提供者接口与至少一个可用实现
- 代码分析、适配器生成、测试执行的核心插件
- 退出条件：端到端流程可用，能在试点项目日常运行

### Phase 2 · 引擎覆盖
- Unity（含 XLua 混合架构）适配
- Unreal 适配
- 跨引擎的契约测试套件
- 退出条件：两个以上真实项目接入

### Phase 3 · 集成形态
- 独立 CLI / Web Dashboard
- REST API / MCP Server
- 作为库嵌入的集成示例
- 退出条件：三种形态都有生产级使用案例

### Phase 4 · 持续运营
- 稳定性、成本、扩展性优化
- 不设退出条件，转入长期演进

## 6. 关于 AI 项目的不确定性

本项目涉及的 LLM、VLM、代码生成能力仍在快速演进：

- 某些能力的边界可能几个月内就会变化
- 单次测试的成本、准确率、延迟在落地前难以精确预测
- 关键依赖（外部 AI 服务）的可用性、合规性存在不确定

应对策略：
- **接口可替换**：所有 AI 能力通过接口调用，实现可随时替换
- **降级路径**：LLM 不可用时可回退到规则驱动或脚本兜底
- **数据驱动**：具体指标（成功率、成本、覆盖率）等真实数据出来后再定阈值，不预设

关键阶段的退出条件以可验证的能力为准，不以数字指标为准。
