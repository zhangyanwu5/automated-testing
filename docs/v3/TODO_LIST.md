# OpenQA v3 - TODO List

> 本文档记录 OpenQA v3 的待办事项，由探讨想法拆解而来。

---

## 待探讨/待细化

- [ ] **检验 AI 结论的可信度** — 系统需要有一项职责：验证 AI 给出的答案/结论是否正确，不能盲目接受 AI 输出
  - 需要考虑的场景：
    - AI 生成的测试用例是否合理？
    - AI 的测试结论（pass/fail）是否准确？
    - AI 的代码审查结论是否有依据？
  - 可能的实现方向：
    - 结论可信度评分机制
    - AI 推理链/依据记录
    - 人工复核触点
    - 自动交叉验证（多模型？）

## 已明确的 TODO

### 命令与交互

- [ ] **长时间执行操作的进度反馈** — 某些函数执行时间较长但无任何输出，用户会以为卡死
  - 需要加进度提示：spinner、进度条、或定期输出当前状态
  - 区分场景：Python 脚本执行时间长 vs AI 推理时间长
  - 目标：让用户明确感知系统还在工作，没有卡死

- [ ] **Slash Command 移至子文件夹** — 参考 OpenSpec 的组织方式，将 oqa 命令放在 `commands/oqa/` 子文件夹下，避免与其他工具命令混在一起

- [ ] **debug 命令的打包区分** — 利用现有 `--pack` flag，在正式包中屏蔽 `debug` 子命令，仅开发模式可用
  - 构建时根据 `--pack` 写入 `_build.py` 标记文件
  - Python 运行时读标记决定是否注册 `debug` 子命令
  - `_build.py` 加入 `.gitignore`

- [ ] **Slash Command 去掉参数，改为自由文本** — 所有 `/oqa:*` 命令后接用户随意输入的内容，由 AI 从自然语言中提取意图，不解析参数

### 流程设计

- [ ] **`run` 支持自动 apply 模式** — 用户通过自然语言描述意图（如"准备好直接跑"），AI 判断是否在准备完成后自动执行 apply，无需用户手动触发

### AI 行为准则

- [ ] **卡点自查机制** — 规划或执行测试时，如果发现卡点，AI 必须先自查，确认无误后再下结论
  - 自查方向：
    - 是不是自己（AI）的分析/理解有问题？
    - 是不是自动化脚本实现的有问题？
  - 只有在排除自身错误后，才能给出"确实是卡点/失败"的结论
  - 目的：避免 AI 把自己的错误归因给用户代码

- [ ] **非阻塞卡点处理** — 遇到有问题的点，确认不是真正卡点后，应跳过或绕过，继续测试后续内容
  - 判断标准：该问题是否阻塞整体测试目标？
  - 非阻塞时：记录问题 → 跳过/绕过 → 继续后续测试
  - 目的：最大化测试覆盖率，不因单点问题放弃整体
